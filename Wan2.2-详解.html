Wan 2.2 从原理到源码：全面详解

Wan 2.2 没有更换范式，而是把「同一套 Flow Matching DiT 地基」升级成了 MoE 双专家 + 高压缩 VAE + 统一 T2V/I2V 的形态。本文从设计原理讲到逐行源码：MoE 的 SNR 切换、Wan2.2-VAE 的 4×16×16 结构、TI2V-5B 的首帧替换与 per-token timestep，全部对照官方仓库代码拆解。

01Wan 2.2 是什么

一句话：Wan 2.2 是阿里巴巴通义万相团队于 2025 年 7 月 28 日开源的视频生成基础模型重大升级——业界首批开源的 MoE（专家混合）视频生成模型，同时附带一个能跑在 RTX 4090 上的 720P@24fps 统一文/图生视频小模型。

1.1 基本事实

  • 发布时间：2025 年 7 月 28 日，Apache 2.0 协议（商用友好），权重同时放在 HuggingFace 与 ModelScope。官方口径：Wan 系列累计下载量当时已超 540 万次。
  • 定位：Wan 2.1（2025 年 2 月）的直系升级版。训练数据相对 2.1 图像 +65.6%、视频 +83.2%，模型能力聚焦四个方向：复杂运动、指令遵循、物理规律、电影级美学。
  • 两大旗舰：
    • A14B 系列（MoE）：把一个去噪过程拆给两个 14B 专家——高噪专家管「构图布局」，低噪专家管「细节精修」。总参数 27B，每步只激活 14B，推理成本不变、模型容量近乎翻倍。
    • TI2V-5B（高压缩统一模型）：5B 稠密模型 + 压缩比 4×16×16 的新 VAE，一个模型同时做文生视频和图生视频，720P、24fps、121 帧（约 5 秒），单张 RTX 4090 不到 9 分钟一条——官方称其为最快的 720P@24fps 开源模型之一。
  • 生态全家桶：同期开源语音驱动数字人 S2V-14B（配套论文 arXiv:2508.18621），2025 年 11 月又补上角色动画模型 Wan2.2-Animate-14B。

1.3 与 Wan 2.1 的关系：先记住「三个不变、四个升级」

Wan 2.2 不是推倒重来。训练目标（Flow Matching）、主干结构（DiT + 3D RoPE + AdaLN）、文本编码器（umT5-XXL）完全沿用 2.1；甚至 A14B 系列用的 VAE 还是 2.1 那颗 Wan2.1_VAE.pth。真正升级的是四件事：

  • 模型组织方式：单模型 → MoE 双专家（第 3 章）；
  • 压缩率：新设计 4×16×16 的 Wan2.2-VAE（第 4 章）；
  • 任务统一：TI2V-5B 用「首帧 latent 替换 + per-token timestep」把 T2V 和 I2V 装进一个模型（第 5 章）；
  • 数据与美学：更大规模 + 带电影维度标注的美学数据（第 9 章）。

02总览：改了什么，没改什么

先把 Wan 2.1 打下的地基用十分钟复习一遍（2.2 一字未改），再看 2.2 的升级地图和一张整体架构图——之后每一章展开一个升级点。

2.1 十分钟复习：2.2 完全沿用的地基

（1）潜空间扩散：先压后生成

视频像素太贵，生成过程全部发生在 VAE 的潜空间（latent space）：encoder 把视频压成低维张量，扩散模型只在 latent 上去噪，最后一步 decoder 还原像素。2.1 的 Wan-VAE 压缩比是 4×8×8（时间×高×宽）、latent 通道 16；A14B 系列继续用它，TI2V-5B 换成 2.2 新设计的 4×16×16、通道 48（第 4 章）。

（2）Flow Matching：直线搬运噪声

训练时在干净 latent x₁ 与高斯噪声 x₀ 之间做线性插值，让网络学「把噪声搬向数据」的速度场：

xt = (1 − t) · x0 + t · x1，    v* = x1 − x0 t∈[0,1]，t=0 纯噪声、t=1 纯数据；路径是直线，ODE 数值积分几十步就够
LFM = Ex₁, x₀, t [ ‖ vθ(xt, t) − (x1 − x0) ‖² ]

推理从纯噪声出发，沿预测的速度场积分回数据。Wan 2.2 的训练目标、timestep 范围（0~1000）与这条公式完全不变。

（3）DiT 主干：3D RoPE + 逐层调制

去噪网络是一个扩散 Transformer（DiT）：latent 先经 Conv3d(patch_size) 切 patch 变 token；每个 block 是「self-attention（全 token 时空联合，配 3D RoPE）→ cross-attention（吃 umT5 文本 token）→ FFN」，self-attention 与 FFN 用 6 路时间调制（AdaLN 风格：shift / scale / gate 各两对）。2.2 的 WanModel 结构与 2.1 基本一致，改动集中在「时间步可以逐 token 不同」（第 6 章）。

（4）CFG 与 shift

vcfg = vuncond + w · (vcond − vuncond) 每步做两次前向（条件/无条件）再外推；负向提示词沿用官方那段中文长句

shift 是噪声调度重参数化：σ' = s·σ / (1 + (s−1)·σ)，把采样步向前（高噪声段）集中——先生骨架、再长细节。2.2 里 T2V-A14B 的推荐 shift 从 2.1 的 3~5 提高到了 12.0（更激进的课程感），TI2V-5B 用 5.0。

2.4 压缩率的算术：为什么 TI2V-5B 快

以「生成 720P、5 秒视频」为例算一笔 token 账（token 数 = latent 帧 × (高/VAE_stride/patch) × (宽/VAE_stride/patch)）：

A14B（1280×720, 81帧）：latent 16×21×90×160 → patch(1,2,2) 后 45×80×21 = 75,600 tokens 每个 token 代表 4×16×16 = 1024 个像素
TI2V-5B（1280×704, 121帧）：latent 48×31×44×80 → patch(1,2,2) 后 22×40×31 = 27,280 tokens 每个 token 代表 4×32×32 = 4096 个像素

同为 720P 五秒：TI2V-5B 的 token 数只有 A14B 的 约 1/2.8，模型参数又是 14B → 5B（约 1/2.8）；线性部分计算量约为 1/8，而注意力是 token 数的平方项，实际还更省。这就是「5B 模型跑 24fps 121 帧、4090 九分钟一条」的来源：不是魔法，是每个 token 管更大的时空范围，再用数据与训练把「粗粒度」的画质补回来。

代价也在明面上

压缩率越高，重建越难、生成越容易糊。Wan 团队在 2.1 技术报告里说过 16× 空间压缩会伤质量——2.2 敢用 4×16×16，是因为 Wan2.2-VAE 的结构专门为此重新设计过（第 4 章：patchify 捷径、注意力挪到瓶颈层、更深的 decoder）。A14B 旗舰仍然用 8× 空间压缩的旧 VAE，就是质量优先的选择。

03MoE 双专家：按噪声水平分工

MoE（Mixture-of-Experts，专家混合）是大语言模型的经典省算力扩容术：参数总量翻倍，但每步只激活一部分。Wan 2.2 把它搬进视频扩散模型时做了一个关键改造——不按 token 路由，按去噪阶段（噪声水平）切换专家。

3.1 为什么扩散模型天然适合「按噪声分工」

回忆一下去噪过程在做什么：从纯噪声（t=1000）走到干净数据（t=0）。不同阶段的任务其实根本不是一件事：

  • 高噪声阶段（早期）：信号几乎被噪声淹没，模型只能决定「低频结构」——画面里有什么主体、摆在哪里、镜头怎么运动。粗略地说，这是在画构图草稿。
  • 低噪声阶段（后期）：结构已经确定，模型做的是把纹理、材质、光影、微表情这些高频细节填对。这是在精修上色。

既然两个阶段的能力画像不同，那就给它们各配一个「术业有专攻」的模型：

  • 高噪专家（high-noise expert）：约 14B 参数，负责去噪早期，专注整体布局；
  • 低噪专家（low-noise expert）：约 14B 参数，负责去噪后期，专注细节优化。

两个专家合计 27B 参数，但每个去噪步只有一个专家在前向——所以单步计算量和显存几乎等于一个 14B 稠密模型，而模型总容量近乎翻倍。这与 LLM 里「稀疏激活的 MoE 层」思想同源，但粒度完全不同（LLM 是每个 token 路由到不同 FFN 专家；Wan 2.2 是整段时间轴切成两段，各自用一个完整模型）。

图 3-1 MoE 双专家的分工与切换。切换点由 SNR（信噪比）决定：SNR 随 t 单调下降，官方把阈值定义在 SNR = SNRmin/2 对应的时间步；代码里落地为固定的 timestep 边界（T2V 0.875、I2V 0.900，乘以 1000）。

3.2 切换点：SNR 叙述与代码实现

官方博客的表述是：SNR 随去噪步 t 增大而单调下降；去噪开始时 t 最大、SNR 处于最小值 SNRmin，此阶段激活高噪专家；阈值步 tmoe 定义为 SNR(tmoe) = SNRmin / 2 对应的时间步，当 t < tmoe 时切换到低噪专家。

落到代码里，「一半 SNR」被固化成一个常数 boundary（训练时定好的调度下界），推理时只做一次数值比较：

def _prepare_model_for_timestep(self, t, boundary, offload_model):
    r"""
    Args:
        t (torch.Tensor): current timestep.
        boundary (`int`): The timestep threshold. If `t` is at or above
            this value, the `high_noise_model` is considered as the required model.
        offload_model (`bool`): A flag intended to control the offloading behavior.
    """
    if t.item() >= boundary:                  # 高噪声段 → 高噪专家
        required_model_name = 'high_noise_model'
        offload_model_name = 'low_noise_model'
    else:                                      # 低噪声段 → 低噪专家
        required_model_name = 'low_noise_model'
        offload_model_name = 'high_noise_model'

    if offload_model or self.init_on_cpu:      # 显存不够时：换出旧专家、换入新专家
        if next(getattr(self, offload_model_name).parameters()).device.type == 'cuda':
            getattr(self, offload_model_name).to('cpu')
        if next(getattr(self, required_model_name).parameters()).device.type == 'cpu':
            getattr(self, required_model_name).to(self.device)
    return getattr(self, required_model_name)
两个值得注意的工程细节

① 硬切换，无 router：代码里没有任何路由网络或概率混合，切换瞬间直接换模型，衔接的平滑性完全靠两个专家在各自噪声区间上的训练分布一致来保证；② 权重是「两份完整的 14B」：不开 offload 时，双专家需要约 2×14B 的显存——所以官方单卡命令（80GB）都带 --offload_model True，切换时把不用的专家搬到 CPU，同一时刻 GPU 上只有一个 14B。

3.3 双 CFG：引导强度也分段

注意上面代码里的 sample_guide_scale = (3.0, 4.0)——这是 2.2 新增的细节：高噪段用更强的引导（4.0），低噪段用更弱的引导（3.0）。直觉上：

  • 高噪段正在定布局，需要文本「大声说话」，把主体和场景钉死——CFG 大一点，指令遵循更好；
  • 低噪段在画细节，过强的引导会放大对比度、过饱和、运动过猛——CFG 收一点，细节更自然。

视频生成的成本大头在推理算力（一条视频几十次 14B 前向），训练成本虽也翻倍但一次性。MoE 用「训练多花钱」换「推理容量翻倍而不涨价」，恰好打在痛点上。另外注意：40 步采样中，由于 shift=12 把时间步向前集中，落在高噪专家区间的步数并不少——两个专家的工作量大体均衡，不存在一个专家闲置浪费。

04Wan2.2-VAE：4×16×16 高压缩编码器

TI2V-5B 快的根源不在 DiT，而在它脚下这颗新 VAE：把视频在时间×高×宽上压 4×16×16（总压缩率 64），再靠 DiT 的 patchify 额外再乘 2×2——每个 token 最终代表 4×32×32 = 4096 个像素。本章拆开 wan/modules/vae2_2.py（约 1050 行）看它怎么做到「压得更狠、还原得还好」。

4.1 设计约束：为什么要重造一颗 VAE

720P@24fps、121 帧的原始张量是 3 × 121 × 704 × 1280 ≈ 3.3 亿个数值。若沿用 2.1 的 4×8×8 压缩，latent 是 16 × 31 × 88 × 160，patchify 后仍有 8.7 万 token——5B 模型跑不动。压到 4×16×16 后 latent 只有 48 × 31 × 44 × 80，patchify 后 2.7 万 token。

难点在 16× 的空间压缩很伤重建质量（2.1 技术报告明确吐槽过这一点）。Wan2.2-VAE 的应对是一套组合拳：

  • 通道数换信息：latent 通道从 16 提到 48——压掉的空间分辨率部分转移到通道维，总数据量压缩其实只有 64/48 ≈ 1.33 倍（对比 2.1 VAE 的 48 倍），省的是 token 网格而不是总信息量；
  • 注意力只放瓶颈层：整个网络只有 encoder/decoder 中央各一个注意力块（逐帧 2D、单头），避开高分辨率的昂贵注意力；
  • decoder 更深：每个上采样 stage 比 encoder 多一个残差块（3 vs 2），把「从粗 latent 还原细节」的重活留给解码端。

4.2 总体结构

实例化参数：z_dim=48（latent 通道）、c_dim=160（encoder 基础宽度）、decoder 基础宽度 256、dim_mult=[1,2,4,4]、temperal_downsample=[False, True, True]。结构上分五段：

图 4-1 Wan2.2-VAE 的 Encoder3d 数据通路（decoder 为镜像结构：宽度 256 起步、每 stage 3 个 ResBlock、DupUp3D 上采样捷径、末尾 unpatchify 还原 3 通道）。

每个基本块长什么样

  • ResidualBlock：RMS_norm → SiLU → CausalConv3d → RMS_norm → SiLU → Dropout → CausalConv3d，shortcut 是 1×1×1 因果卷积；
  • Down_ResidualBlock：主体若干 ResBlock + Resample 下采样，shortcut 走 AvgDown3D——按「时间×空间」分组取平均的下采样捷径，参数自由、训练稳定；
  • Resample(downsample3d)：空间用「右侧/下侧补零 + stride-2 的 3×3 Conv2d」（不对称 padding 是 causal 风格的延续），时间用 CausalConv3d(kernel=(3,1,1), stride=(2,1,1)) 只看过去地隔帧抽取；
  • AttentionBlock：把 (B,C,T,H,W) 重排成 (B·T, H·W, C) 做逐帧 2D 单头 self-attention，输出投影零初始化（训练初期等于恒等，不破坏 VAE 的收敛）；
  • Decoder 侧镜像：Up_ResidualBlock 的捷径是 DupUp3D（复制重排上采样，首块丢掉多余的时间帧），上采样主路 = 最近邻上采样 2D + 时间维用「通道翻倍 + 交错重排」恢复帧数。

4.3 首帧规则：为什么 latent 帧数 = 1 + (T−1)/4

两级时间下采样各压 2 倍，理论上 T 帧应压成 T/4；但因果卷积「不看未来」意味着第一帧没有历史，走的是特殊路径。实现上，encode 被切成 chunk 逐块处理：

wan/modules/vae2_2.py · WanVAE_.encode()Python
def encode(self, x, scale):
    self.clear_cache()
    x = patchify(x, patch_size=2)          # 3ch → 12ch，空间 /2
    t = x.shape[2]
    iter_ = 1 + (t - 1) // 4               # 121 帧 → 1 + 30 = 31 个 chunk
    for i in range(iter_):
        self._enc_conv_idx = [0]
        if i == 0:
            out = self.encoder(            # 第 0 块：只送入首帧（1 帧）
                x[:, :, :1, :, :],
                feat_cache=self._enc_feat_map,
                feat_idx=self._enc_conv_idx)
        else:
            out_ = self.encoder(           # 之后每块送 4 帧
                x[:, :, 1 + 4 * (i - 1):1 + 4 * i, :, :],
                feat_cache=self._enc_feat_map,
                feat_idx=self._enc_conv_idx)
            out = torch.cat([out, out_], 2)
    mu, log_var = self.conv1(out).chunk(2, dim=1)     # 96ch → μ, log_var
    if isinstance(scale[0], torch.Tensor):
        mu = (mu - scale[0].view(1, self.z_dim, 1, 1, 1)) * scale[1].view(
            1, self.z_dim, 1, 1, 1)                   # 逐通道 (μ-mean)·(1/std)
    else:
        mu = (mu - scale[0]) * scale[1]
    self.clear_cache()
    return mu
  • 第 0 块只含 1 帧：两级时间下采样对首个 chunk 不生效（没有历史 cache，Resample 直接跳过 time_conv）→ 首帧独占 1 个 latent 帧；
  • 之后每 4 帧一块：4 帧被两级 ×2 时间下采样压成 1 个 latent 帧。所以 T 帧视频 → 1 + (T−1)/4 个 latent 帧，121 帧 → 31；
  • 单帧图像（T=1）走的就是第 0 块路径，得到 1 个 latent 帧——「图片」和「视频首帧」是完全同一条代码路径，这正是第 5 章 TI2V 统一 T2V/I2V 的基础。

decode 完全镜像：逐 latent 帧送入 decoder，第 0 个 latent 帧（first_chunk=True）恢复出 1 个像素帧，之后每个 latent 帧恢复 4 个像素帧：

wan/modules/vae2_2.py · WanVAE_.decode()Python
def decode(self, z, scale):
    self.clear_cache()
    if isinstance(scale[0], torch.Tensor):
        z = z / scale[1].view(1, self.z_dim, 1, 1, 1) + scale[0].view(
            1, self.z_dim, 1, 1, 1)                   # 反归一化
    else:
        z = z / scale[1] + scale[0]
    iter_ = z.shape[2]                                # 逐 latent 帧流式解码
    x = self.conv2(z)
    for i in range(iter_):
        self._conv_idx = [0]
        if i == 0:
            out = self.decoder(                       # 首个 latent 帧 → 1 个像素帧
                x[:, :, i:i + 1, :, :],
                feat_cache=self._feat_map,
                feat_idx=self._conv_idx,
                first_chunk=True)
        else:
            out_ = self.decoder(                      # 之后每个 latent 帧 → 4 个像素帧
                x[:, :, i:i + 1, :, :],
                feat_cache=self._feat_map,
                feat_idx=self._conv_idx)
            out = torch.cat([out, out_], 2)
    out = unpatchify(out, patch_size=2)               # 12ch → 3ch，空间 ×2
    self.clear_cache()
    return out

4.4 因果卷积与流式 cache：分块推理的等价性

CausalConv3d 继承 nn.Conv3d，但时间维只在「过去」方向 padding（k=3 时在序列前面 pad 2 帧、后面 pad 0）——只看历史不看未来。这带来一个关键能力：长视频可以切成 chunk 流式编解码。实现方式是给每个 CausalConv3d 配一个 cache 槽：

        # 把 padding 重排成 F.pad 顺序，并把 self.padding 置零——

    ih, iw = img.height, img.width

dh = dw = patch_size × vae_stride = 2 × 16 = 32：对齐单位不是 VAE 步长 16，而是「VAE 步长 × patch」，保证裁出来的尺寸既能被 VAE 整除、token 网格也不会出半格。这是 TI2V 的尺寸必须从 1280×720 改成 1280×704 的根本原因（704 = 22×32，整除干净）。best_output_size() 内部先按原始宽高比算出面积封顶的目标尺寸，再比较「先对齐宽」和「先对齐高」两种取整方案，选宽高比偏移更小的一个——所以输出宽高比跟随输入图，横图出横视频、竖图出竖视频。

        latent_model_input = [latent.to(self.device)]
        timestep = torch.stack([t]).to(self.device)

        # ② per-token timestep：首帧 token 得到 0，其余 token 得到 t，补齐到 seq_len
        temp_ts = (mask2[0][0][:, ::2, ::2] * timestep).flatten()
        temp_ts = torch.cat([temp_ts, temp_ts.new_ones(seq_len - temp_ts.size(0)) * timestep])
        timestep = temp_ts.unsqueeze(0)                     # 形状 [1, seq_len]：每个 token 一个时间步

        noise_pred_cond = self.model(latent_model_input, t=timestep, **arg_c)[0]
        noise_pred_uncond = self.model(latent_model_input, t=timestep, **arg_null)[0]
        noise_pred = noise_pred_uncond + guide_scale * (noise_pred_cond - noise_pred_uncond)

        temp_x0 = sample_scheduler.step(                   # UniPC / dpm++ 走一步
            noise_pred.unsqueeze(0), t, latent.unsqueeze(0),
            return_dict=False, generator=seed_g)[0]
        latent = temp_x0.squeeze(0)
        latent = (1. - mask2[0]) * z[0] + mask2[0] * latent # ③ 每步结束：把首帧重新钉回图像（同一条公式）
latent ← (1 − mask) · z0 + mask · latent      timesteptoken = masktoken · t（首帧 token = 0） 两个操作都只依赖同一个 mask：第 0 帧 = 图像 latent + t=0，其余帧 = 去噪进度 + 当前 t

为什么 ①③ 必须重复执行：求解器并不知道哪些帧是条件，step() 会平等地「推进」全部 31 帧，把首帧也稍微动一下——所以每一步后都要把首帧重新覆盖回去，否则 50 步累积下来首帧早就漂了。

per-token timestep 的三行值得逐个拆开（对照图 5-1）：

  • mask2[0][0]——mask2[0] 形状 [48, 31, 44, 80]，再取 [0] 拿到通道 0，得到 [31, 44, 80]。48 个通道的值完全相同，任取一个都行，取 0 号只是最省事的「代表」；
  • [:, ::2, ::2]——时间维全取、高宽隔 2 取 1，正好模拟 patch (1, 2, 2) 的取格方式：[31, 44, 80] → [31, 22, 40]，一个元素对应一个 token；
  • × timestep 再 flatten()——mask 在第 0 帧是 0、其余帧是 1，于是首帧的 880 个 token（22×40）得到 t=0，其余 26,400 个 token 得到当前时间步 t；
  • torch.cat(...new_ones(seq_len - len) * timestep)——把长度补齐到 seq_len（序列并行时向上取整的余位），补位的 token 也标成 t；最后 unsqueeze(0) 成 [1, seq_len] 的 2D timestep。

图 5-1 TI2V 的两个核心操作。同一个 mask 驱动两件事：latent 域把第 0 帧钉在图像 latent 上（上），token 域把首帧 token 的时间步改成 0（下）。t=0 在 Flow Matching 里意味着「纯数据」——模型对这 880 个 token 的理解是「这一帧已经完全去噪好了」。

为什么 t=0 是「正确」的语言

回忆第 2 章：xt = (1−t)·x0 + t·x1，t=0 时就是干净数据本身。把首帧 token 的时间步设为 0，等于直接告诉模型「这帧不存在噪声，不需要去噪」；而首帧 latent 又确实是从图像 encode 出来的干净数据——声明与事实一致，模型不需要任何新结构就能理解这个条件。这也是为什么每步重钉之后不会和求解器冲突：对首帧 token 而言 t 恒为 0，模型对它们的预测始终是「保持原样」。

5.6 masks_like()：留在推理代码里的训练痕迹

两个 mask 来自这个不起眼的工具函数——它同时也是训练策略的活化石：

wan/utils/utils.py · masks_like()Python
def masks_like(tensor, zero=False, generator=None, p=0.2):
    assert isinstance(tensor, list)
    out1 = [torch.ones(u.shape, dtype=u.dtype, device=u.device) for u in tensor]
    out2 = [torch.ones(u.shape, dtype=u.dtype, device=u.device) for u in tensor]
    if zero:
        if generator is not None:                      # 训练分支（推理时 generator=None，不走这里）
            for u, v in zip(out1, out2):
                random_num = torch.rand(1, generator=generator, ...).item()
                if random_num < p:                      # 20% 概率：首帧权重 = exp(N(-3.5, 0.5))
                    u[:, 0] = torch.normal(mean=-3.5, std=0.5, size=(1,), ...).expand_as(u[:, 0]).exp()
                    v[:, 0] = torch.zeros_like(v[:, 0])
                else:                                  # 80% 概率：保持全 1（首帧不特殊）
                    u[:, 0] = u[:, 0]
                    v[:, 0] = v[:, 0]
        else:                                          # 推理分支：第 0 帧严格置 0
            for u, v in zip(out1, out2):
                u[:, 0] = torch.zeros_like(u[:, 0])    # u[:, 0] = 通道维 [:, 0]：第 0 个 latent 帧的 48 个通道
                v[:, 0] = torch.zeros_like(v[:, 0])
    return out1, out2

读法：两个输出 mask 的形状与输入完全相同（[48, 31, 44, 80]），u[:, 0] 里的索引 0 落在时间维上——即第 0 个 latent 帧的全部 48 通道。三种行为：

  • zero=True 且无 generator（i2v 推理）：mask1、mask2 的第 0 帧都置 0，其余全 1——首帧被严格钉死，timestep 严格为 0；
  • zero=True 且有 generator（训练）：80% 的样本 mask 保持全 1（首帧当普通噪声帧训练，等价 T2V 数据）；20% 的样本 u[:, 0] = exp(N(−3.5, 0.5))——中位数 ≈ 0.03，绝大多数落在 0.01~0.08，即首帧 latent 由「3% 左右的噪声 + 97% 的干净图像」构成，同时 v[:, 0] = 0 让 timestep 为 0（I2V 数据，但首帧故意带一点扰动）；
  • zero=False（t2v）：整段 if 跳过，mask 全 1——没有任何帧被特殊对待。
官方未说明的部分（推断）

这个 20% 概率的小系数（≈0.01~0.08）在 README 和博客中都没有解释。合理推断是训练时的随机化：一方面模拟 VAE 重建与真实噪声带来的首帧不完美，让推理时「严格置 0」的策略落在训练分布附近；另一方面大约 1:4 的比例混训「有首帧条件 / 无首帧条件」的样本，正是同一权重能同时服务两个任务的训练基础。此段为代码行为推断，非官方结论。

为什么能删？2.1 的 I2V 走「双编码器」路线：除了把首帧 latent 拼进 in_dim 通道，还要把 CLIP ViT-H 的 1280 维图像特征投影后拼进 cross-attn 的 context（每图 257 个 token 的「全局图像语义」）。2.2 只保留前一条路线——首帧信息完全靠 latent 通道传递，文本侧只喂 UMT5 特征。这是主线上一次明确的减法：删掉一条信息通路，换来主干对所有 model_type 的完全统一。净减的 85 行，主要就是这条分支的类定义、断言、forward 参数与拼接逻辑。

in_dim 的「+1」传言：源码证伪

网上流传「2.2 的 in_dim 会 +1 存一个额外通道」的说法。对照源码可以澄清：两版都是 self.in_dim = in_dim 的直接赋值，没有任何 +1 逻辑。in_dim 的三档取值完全由 config.json 指定：16 = 纯噪声 latent；36 = 16 噪声 + 20 条件通道（首帧 VAE 特征与逐帧掩码在 image2video.py 里拼装，详见第 8 章）；48 = Wan2.2 高压缩 VAE 的 latent 通道数。通道拼接收敛在数据管道里，主干里没有魔法。

去掉所有语法噪音后，每个 block 的数学骨架两版完全一致：

attn_in = norm1(x) ⊙ (1 + e1) + e0
x = x + self_attn(attn_in) ⊙ e2
ffn_in = norm2(x) ⊙ (1 + e4) + e3
x = x + ffn(ffn_in) ⊙ e5 e0…e5 即 e0 按 6 切 chunk 的结果：e0/e3 是 shift（偏置）、e1/e4 是 scale（缩放）、e2/e5 是 gate（门控残差）。三件套作用于 self-attention 与 FFN 两处，cross-attention 完全不参与调制。

「搬家」搬的是什么？把两行关键代码的形状标注出来就清楚了：

  • 2.1：e 是 [B, 6, C]，modulation 是 [1, 6, C]——相加时广播发生在 batch 维，chunk(dim=1) 切出六片 [B, C]。每个序列一组参数，整段视频共享。
  • 2.2：e 是 [B, L, 6, C]，modulation.unsqueeze(0) 是 [1, 1, 6, C]——广播发生在 batch 维与 token 维两处，chunk(dim=2) 切出六片 [B, L, 1, C]，再 squeeze(2) 成 [B, L, C]。每个 token 一组参数；同一个 modulation 偏置对全序列仍然一致，逐 token 变化的部分全部来自 e0。

三处工程细节值得单独点名：其一，float32 孤岛——调制链路全程被 torch.amp.autocast('cuda', dtype=torch.float32) 包裹，前后各有一个 assert 验证 dtype。在 bf16 混合精度训练/推理中，shift/scale 参数的精度损失会直接毁掉去噪轨迹，所以官方把这条链隔离成精度孤岛（2.1 已是如此，2.2 逐字沿用，只是作用域跟着 e 一起搬家）。其二，参数名——这个 [1, 6, dim] 张量在 diffusers 社区的同名机制里通常叫 scale_shift_table，Wan 里叫 modulation。其三，初始化——torch.randn(1, 6, dim) / dim**0.5 是非零随机初始化：Wan 借用了 AdaLN 的形状与用法，但没有采用 DiT 论文 AdaLN-Zero 的「gate 零初始化」技巧（初始 gate≈1，且训练后未必接近零），说「Wan 用 AdaLN-Zero」并不准确。

第二个不变项是 unpatchify——把 token 流还原成视频张量。这是全文件唯一一处「魔法密度」最高的代码，七字母 einsum 一行做完空间重组：

wan/modules/model.py · WanModel.unpatchify()（第 499–522 行，与 2.1 相同）Python
    def unpatchify(self, x, grid_sizes):
        c = self.out_dim
        out = []
        for u, v in zip(x, grid_sizes.tolist()):
            u = u[:math.prod(v)].view(*v, *self.patch_size, c)
            u = torch.einsum('fhwpqrc->cfphqwr', u)
            u = u.reshape(c, *[i * j for i, j in zip(v, self.patch_size)])
            out.append(u)
        return out

七字母各管一轴：f/h/w 是 patch 网格三轴（latent 帧数、高、宽方向的 patch 数，即 grid_sizes），p/q/r 是 patch_size (1, 2, 2) 三轴，c 是 out_dim 通道。view 把每个 token 的 64 个数解释为 [p, q, r, c] 的小立方体，einsum 把轴重排成 [c, f, p, h, q, w, r]——三个 patch 内小轴交错插回三个网格轴后面，reshape 合并 (f,p)→F、(h,q)→H、(w,r)→W，得到 [C, F, H, W]。另一处细节在行首：u[:math.prod(v)] 先裁掉补零 token——6.3 里 padding 进来的那些位置，在出口处被精确丢弃。

  • 读数二：TI2V 是家族唯一的新宽度。3072/14336/24×30，ffn/dim = 4.67（A14B 只有 2.7；2.1 的 1.3B 是 5.83）——小模型普遍用更宽的 FFN 换参数效率。头维保持 128，意味着 RoPE 的 44:42:42 划分无需任何改动即可复用，6.5 的不变项正是这样被「免费」继承的。
  • 读数三：新 VAE 只服务 TI2V。三个 14B 级仓库（A14B/S2V/Animate）携带的都是 Wan2.1_VAE.pth，唯独 TI2V-5B 带 Wan2.2_VAE.pth——高压缩 VAE 是 5B 模型的专属提速件，与质量旗舰无关。S2V 与 Animate 则是「14B 骨架 + 外挂」的产物（音频注入层、动作编码器），细节留到第 8 章。
「27B」的实测口径

README 原文：「Each expert model has about 14B parameters, resulting in a total of 27B parameters but only 14B active parameters per step」。实测更精确：T2V-A14B high_noise_model 的权重索引 total_size = 57,153,966,336 字节，fp32 存储 ÷4 = 14.288B 参数；low_noise_model 的 config 与字节尺寸与之完全相同（同一数字）；双专家合计 28.58B，官方 27B 是约数。手算互证：每块 self-attn ≈1.05 亿 + cross-attn ≈1.05 亿 + FFN ≈1.42 亿 ≈ 3.51 亿，×40 层 = 14.06B，加嵌入与 time_projection ≈0.23B = 14.29B——两路误差 <0.001B。TI2V-5B 同法：19,999,150,848 ÷ 4 = 5.0B。权重以 fp32 发布，正是单卡命令建议 --convert_model_dtype（转 bf16 体积与显存减半）的原因。

系统内存账：offload 的隐性门槛

单卡默认 init_on_cpu=True + offload 意味着两个 fp32 专家共 57.15 GB × 2 ≈ 114 GB 长期驻留系统内存（RAM），而不是显存。显存侧每次只需装下一个专家（fp32 全量 57 GB，或 --convert_model_dtype 后 28.6 GB）。这就是「单张 4090（24 GB 显存）能跑 A14B」的代价结构：显存不够、内存来凑，专家切换时在 PCIe 上搬运一次完整权重。RAM 不足的机器会在加载阶段就 OOM——升级显存之前，先看内存条。

代入 T2V-A14B 的默认参数（1280×720、81 帧）走一遍：Tf = 80/4 + 1 = 21，Hf = 720/8 = 90，Wf = 1280/8 = 160，于是 L = 90 × 160 / 4 × 21 = 3600 × 21 = 75600。这个数字正是第 6 章反复出现的 e0 = [1, 75600, 6, 5120] 的 75600——同一个序列长度，在第 6 章是显存账单（6 × 5120 × 75600 × 4B ≈ 9.3 GB），在这里是分辨率的直接产物。换 TI2V-5B 算一遍（704×1280 竖屏、121 帧、新 VAE 压 16×）：Tf = 31，Hf = 80，Wf = 44，L = 80 × 44 / 4 × 31 = 27280，对应 e0 ≈ 27280 × 6 × 3072 × 4B ≈ 2.0 GB——第 5 章那张显存对比表的出处即在于此。

顺带解开一个常见疑问：为什么帧数必须是 4n+1（81、121、77……）？看 (F − 1) // 4 + 1 就明白了——Wan 的 VAE 时间压缩是因果式的，首帧单独编一帧 latent，其后每 4 帧压成 1 帧。若 F 不是 4n+1，末尾不足 4 帧的残段要么丢帧要么补帧，都会破坏帧对齐。CLI 的 --frame_num help 文档那句 "The number should be 4n+1"，说的就是这条约束。

7.4 噪声调度与两个求解器

去噪循环的「时间表」由采样器给出。Wan 2.2 支持 unipc 与 dpm++ 两个求解器（CLI 的 --sample_solver，默认 unipc），但无论选哪个，底层都从同一条公式出发——先把步数铺成均匀的 σ 网格，再用 shift 把网格往高噪声端弯折：

wan/utils/fm_solvers.py · get_sampling_sigmas（第 24–28 行，逐字）Python
def get_sampling_sigmas(sampling_steps, shift):
    sigma = np.linspace(1, 0, sampling_steps + 1)[:sampling_steps]
    sigma = (shift * sigma / (1 + (shift - 1) * sigma))

    return sigma
σ′i = s · σi / (1 + (s − 1) · σi) s 即 sample_shift；σi 是 linspace(1, 0) 的均匀网格，σ′ 恒满足 σ′ ≥ σ（0 < σ < 1, s > 1）：每个采样点都被推向高噪声一端

这条 shift 变换不是 Wan 的发明——它与 SD3 论文的 timestep shift 同源，几何效果可以用导数精确刻画：变换在 σ ≈ 1（高噪端）的局部斜率是 1/s，在 σ ≈ 0（低噪端）是 s。也就是说，原本等间距的采样点经过弯折后，高噪声段的点距被压缩 s 倍（步子变密），低噪段被拉长 s 倍（步子变稀）。用 shift=5 走一遍：σ=0.9 的点被推到 5×0.9/(1+4×0.9) = 4.5/4.6 ≈ 0.978，紧贴纯噪声；σ=0.1 被推到 0.5/1.4 ≈ 0.357，远离干净端。视频生成的构图、运动结构主要在高噪段成形，shift 越大，越多的采样步数被花在「打地基」的阶段。

8.1 一张图变成 20 个通道：I2V 的条件注入

WanI2V（wan/image2video.py，431 行）的构造函数与 WanT2V 逐字同构：T5 常驻 CPU、Wan2.1_VAE 上卡、双专家从 high_noise_model/ 与 low_noise_model/ 子目录加载后躺在系统内存。模型侧与 T2V 的全部区别浓缩成一个数字：in_dim=36——patch_embedding 这层 Conv3d 的输入通道从 16 变成 36。生成侧的差异则有四件事：分辨率不再查表而是由参考图反推、构造 4 通道掩码、构造 16 通道图像条件、CFG 的负向分支也带着图像。逐一来看。

第一件事：分辨率反推。T2V 的尺寸来自 CLI 上的 size 字符串（查第 7 章的 SIZE_CONFIGS 表），I2V 则完全由参考图的宽高比和 max_area 决定——用户传什么形状的图，就生成什么形状的视频：

与 2.1 的对照在此收口：2.1 的 I2V 除了这套 20 通道注入，还额外加载 CLIP 视觉编码器，把参考图的 257 个 token 拼在 cross-attention 的 context 前面（第 6 章表 6-2 记录过 img_emb 路径）。2.2 的 I2V 配置里已无任何 CLIP 字段——图像语义完全交给 VAE latent 通道承载，文本语义完全交给 T5。少加载一个视觉编码器、少一份数据管线，代价则由 VAE 通道的表达力来兜底。有意思的是，这条被 I2V 删掉的 CLIP 路径在 8.3 的 Animate 里原样复活——Animate 的 WanAnimateCrossAttention 里就有那组 k_img / v_img 投影。

I2V 特有的两处显存策略

其一，专家切换被抽成独立方法 _prepare_model_for_timestep（第 172–204 行）：先用 next(model.parameters()).device 检查两个专家当前在哪，只在必要时搬运——比第 7 章 T2V 版的「无条件换人」少一半冗余 PCIe 传输。其二，offload 模式下 I2V 的去噪循环在每次模型前向后都调用 torch.cuda.empty_cache()（第 380、396、400、418 行），密度远高于 T2V 版——y 的编码与双专家交替让显存水位更紧张，必须更积极地归还缓存块。另外 docstring 第 232 行有官方注释：生成 480P 时建议把 shift 降到 3.0（720P 默认 5.0），低分辨率下噪声表需要整体右移才能维持同等清晰度。

            audio_attn_id = self.audio_injector.injected_block_id[block_idx]

                :, :self.original_seq_len].clone()                   # 只处理噪声段 token

                input_hidden_states, "b (t n) c -> (b t) n c", t=num_frames)   # 按帧拆批次

                hidden_states[:, :self.original_seq_len] + residual_out)   # 残差写回

三个要点。其一，rearrange "b (t n) c -> (b t) n c" 把 20 个 latent 帧拆进 batch 维——每个视频帧的 token 独立成批，只与自己那一帧的 4 个音频 token 做交叉注意力，口型与发音的时间对齐由此保证。其二，AdaLN 分支（enable_adain=true）用音频的全局特征生成 LayerNorm 的 scale/shift，注意力还没算、特征先被音频「调音」。其三，zero_init_weights（第 441–454 行）把每个注入器的输出投影 o 与 AdaLN 的 linear 全部零初始化——训练开始时音频旁路输出恒为零，模型从「没有音频」的状态平滑过渡到「有音频」，不扰动预训练权重的起点。这与第 3 章双专家的可加载性、第 5 章适配器的思路同属一族：新增能力一律从零起步。

S2V 的专属负向提示词：为音频驱动定制

s2v_14B 的 config 覆盖了通用负向提示词，全文是：「画面模糊，最差质量，画面模糊，细节模糊不清，情绪激动剧烈，手快速抖动，字幕，丑陋的，残缺的，多余的手指，画得不好的手部，画得不好的脸部，畸形的，毁容的，形态畸形的肢体，手指融合，静止不动的画面，杂乱的背景，三条腿，背景人很多，倒着走」。两条划线项是音频驱动任务特有的病灶：音频会诱导模型「用力表演」（夸张表情与手部抽搐），负向词反向压制；而「静止不动」则是口型同步失败的常见崩坏模式。负向提示词在这里不是泛泛的质量词堆砌，而是对失败模式的精确枚举。

第二路 pose：加性注入。after_patch_embedding 的头三行先处理姿态：姿态视频的 VAE latent（[16, 20, lat_h, lat_w]，20 个 latent 帧与 x 的帧 1..20 对齐）过 pose_patch_embedding 升维到 5120，然后 x_[:, :, 1:] += pose_latents_——逐元素加到 patch 化后的 token 上、跳过帧 0。这与 S2V 的 cond_encoder 完全同构（8.2 读过），区别只在地位：S2V 里姿态是可选辅助，Animate 里姿态是主条件——整个表演的动作全部来自这一路。注入时机在 patch 之后、第一层 transformer block 之前：动作信息从第一层起就参与每一层的自注意力。

第三路 face：表情旁路。再看 after_patch_embedding 的后半：人脸视频（[1, 3, 77, 512, 512]）重排成 77 张独立图片、按 encode_bs=8 分批送进 motion_encoder.get_motion，得到 77 个 512 维向量；重排回 [1, 77, 512] 后交给 face_encoder，内部把时间维 77→39→20 两级下采样（对齐 VAE 的 4× 时间压缩），并把每个 512 维向量翻译成 5 个 5120 维 token，输出 [1, 20, 5, 5120]；最后 pad_face 在时间维前面补一帧全零，对齐到 [1, 21, 5, 5120]——又是帧 0 牺牲位的呼应：表情 token 的帧 0 是零，不给参考图槽位塞任何表情。

这里必须停下来考古。motion_encoder 的真身在 wan/modules/animate/motion_encoder.py，文件头一行注释：# Modified from ``https://github.com/wyhsirius/LIA``——LIA（Latent Image Animator，CVPR 2022），一个 StyleGAN2 时代的表情重演模型，方言扑面而来：EqualLinear、net_app、Generator/Synthesis 的命名全是 GAN 惯例。数据流是：人脸图过 net_app（pSp 风格的编码器）得 512 维特征 → fc 尾层 EqualLinear(512, 20) 压成 20 个系数 alpha → Direction 模块用这 20 个 alpha 对一组正交基做线性组合，回扩成 512 维方向向量。正交基来自哪？Direction.weight 是 [512, 20] 的可学习矩阵，前向时 QR 分解（custom_qr(weight + 1e-8)）得正交 Q，然后 torch.sum(torch.diag_embed(alpha) @ Q.T, dim=1)——20 维系数在 512 维空间里沿 20 个正交方向张成的子空间取点。config 里 motion_encoder_dim=512 与 FaceEncoder 的 in_dim=512 互证：LIA 吐出的就是 512 维方向向量（20 只是系数个数，不是输出维度）。还有一处指纹：get_motion 用 gradient checkpointing 包住编码器、用 fp32 autocast 包住 Direction——训练与推理共用同一个函数，训练时的显存与精度考量原样留在了推理代码里。

FaceEncoder（face_blocks.py 第 128–176 行）是「LIA 方言 → DiT 方言」的翻译层：conv1_local 是 CausalConv1d(512, 1024×4, 3)——一次产出 4 个「头」的 1024 维特征；conv2/conv3 是两个 stride=2 的因果卷积，把时间维 77→39→20；out_proj Linear(1024, 5120) 升到主干宽度；最后 cat 上可学习的 padding_tokens——每帧的第 5 个 token 不来自卷积，而是一个全局可学习向量（四头各出一个实 token，第 5 个是「帧级汇总位」）。CausalConv1d 的 pad_mode 是 replicate：第 t 帧的表情 token 只依赖第 ≤t 帧的人脸，不偷看未来——主干 DiT 的自注意力并不因果，但表情编码这条支路自己守住了时序纪律。

FaceBlock 是一个「K/V 与 Q 来自不同源」的交叉注意力：K/V 是 21×5 个表情 token，Q 是当前层的视频 token。两个关键的 rearrange 干同一件事——按帧分组："B L N H D -> (B L) N H D" 把 K/V 变成「每个视频帧一批」；"B (L S) H D -> (B L) S H D" 把 Q 同样按帧切开。于是每个视频帧的 token 只与自己那一帧的 5 个表情 token 做注意力——表情与动作的时间对齐由此保证，与 S2V 的 "b (t n) c -> (b t) n c" 是同一招（8.2 读过）。heads_num=40、head_dim=128，q_norm/k_norm 是 RMSNorm；输出可被 motion_mask 门控（推理传 None，直接放行），残差相加 x = residual_out + x——新增旁路对主干的扰动被限制在残差尺度内。挂载密度也值得对照：S2V 的 12 处注入点前疏后密（末段每 3 层一注），Animate 的 8 处均匀分布（每 5 层一注）——表情是全时段均匀需要的信号，不像音频那般「越接近输出越要细化」。

还有一处实现细节颇堪玩味：FaceAdapter 实际上被绕过了。主干里的调用不是 self.face_adapter(...)，而是直接索引 self.face_adapter.fuser_blocks[block_idx // 5]——FaceAdapter 退化成一个纯粹的容器（ModuleList 的宿主），它自己的 forward 还带着 freqs_cis_q/freqs_cis_k 参数（训练时代的接口风格），推理路径根本不走它。

第四路 CLIP：语义前缀。现在回收 8.1 结尾的伏笔：为什么姿态驱动需要图像语义编码器？想想模型手里的其他信号——姿态视频里的人没有长相（骨架而已）；人脸视频里的人是别人的脸（只有表情可用）；y 通道里参考图只占 21 个 latent 帧中的 1 帧、token 占比不足 5%，还压在 VAE 的低频里。「这个角色长什么样」缺少一路恒定、高频、全局的信号。于是 2.1 I2V 的老配方原样复活：参考图过 XLM-R ViT-Huge 视觉塔得 257 token × 1280 维，img_emb（MLPProj）升到 5120 后拼接在 T5 文本 context 的前面——CLIP token 成为文本序列的「前缀」，每层 cross-attn 都能看到。注意力侧的实现：

LoRA（Low-Rank Adaptation）在预训练权重旁边挂低秩旁路 B @ A，只训练旁路、冻结主干，推理时合并——rank 是旁路的秩，即这次适配可表达改变的「自由度」。风格类适配常见 rank 8～32 就够（改变的是全局色调、笔触这类低维属性）；重打光要重画整幅光照场——高光位置、阴影走向、色温、反射全都要动——所以 rank=128，且 alpha/rank = 1.0（满幅注入，不做缩放）。它只在 replacement 模式下有意义：新角色要「服」老背景的光，两者在 y 通道里同框，LoRA 负责让模型学会这种调和。

LIA 考古：StyleGAN2 方言为何出现在 DiT 仓库

EqualLinear、QR 正交化的「运动基」、Generator/Synthesis 的命名——这是 2022 年 StyleGAN2 时代的方言，被原封不动搬进了 2025 年的 DiT 仓库。这不是工程疏漏，而是务实：Wan 团队的策略一贯是「感知用现成的，生成自己练」——S2V 借 wav2vec2 听音频、全家借 umt5 读文本、Animate 借 LIA 读表情，感知侧的预训练资产直接复用，生成侧的 14B 主干自己训练。顺带一提，get_motion 里的 gradient checkpointing 与 fp32 autocast 是训练脚本的指纹：训练与推理共用同一个函数，训练时省显存、保精度的代码就这样留在了推理路径里。

四路条件至此齐了：y 管身份与背景（通道拼接）、pose 管动作（patch 后加性）、face 管表情（8 个 FaceBlock 旁路）、CLIP 管外观语义（注意力键值前缀）——四种注入方式恰好覆盖了 DiT 的全部入口：输入通道、patch 之后的特征、层间旁路、注意力的 K/V。编码器清点一下：T5（文本）、Wan2.1 VAE（y 与 pose 两用）、LIA + FaceEncoder（表情）、XLM-R ViT-Huge（外观）——一个 14B 主干外挂四套感知前端。上游还有一条预处理链（wan/modules/animate/preprocess/）：DWPose 抽姿态、人脸检测裁切到 512²、SAM 抠人物掩码、FLUX 修补背景——三段输入素材全部由它从一段原始视频自动产出。这个方向在 2026 年 7 月有了后继者 Wan-Animate-2（独立新仓库），而 Wan 2.2 的 Animate 已经把「参考图 + 姿态 + 人脸」的三素材范式立成了行业默认。推理侧的故事到此讲完，下一章掉头看训练侧：数据、美学与基础设施。

9.2 Dense Video Caption：把看图说话练成标注基础设施

漏斗第四层是整套管线里最「模型化」的一环。原始数据的网页配文大多贫弱，撑不起视频生成需要的细粒度图文对齐；DALL·E 3 已经验过一条路：用高度描述性的合成 caption 训练生成模型，prompt 遵循能力会显著提升。于是 Wan 自训了一个 caption 模型，给数据集里的每张图、每条视频重写密集描述——第 1 章提过的「指令遵循」卖点，地基就在这里。

caption 模型是 LLaVA 式结构：ViT 提取视觉嵌入，经两层 MLP 投影进 Qwen LLM。图像走动态高分辨率，最多切成 7 块，每块的视觉嵌入池化到 12×12 网格以省算力；视频按每秒 3 帧采样、上限 129 帧，并用慢-快编码进一步压算力——每 4 帧保留原分辨率，其余帧的嵌入做全局平均池化。长视频基准上这条机制用有限视觉 token 换来更好的理解（报告给出的数字：VideoMME 无字幕成绩 67.6% → 69.1%）。训练分三阶段：先冻结 ViT 与 LLM 只训投影层 MLP（学习率 1e-3）；再全参数放开（LLM 与 MLP 1e-5、ViT 1e-6）；最后用小规模高质量数据做端到端收尾。

喂给这个 caption 模型的标注数据集是一份长清单，每类都对应一项生成能力的靶向补强：

  • 名人、地标、影视角色：LLM 收集名单，CLIP 系模型（报告试过多款，TEAM 在识人尤其中国名人上最好）从图库检索，再用关键词匹配过滤噪声；
  • 物体计数：从含「一、二、三」等字样的描述出发，LLM 抽取（类别， 数量）对，再让 Grounding DINO 数一遍——数对得上才保留；
  • OCR：现成 OCR 先抽文字，caption 模型以抽取结果为先验生成描述，中英文皆收；
  • 镜头角度与运动：现役 MLLM（包括 GPT-4o、Gemini Pro 这类旗舰）在镜头语言上普遍拉胯，Wan 人工标注种子集，要么直接训 caption 模型，要么先训专家标注器再放大标注量；
  • 细粒度类别（动植物、载具等数百万张）、空间关系（借检测数据集练「左右上下」）、re-caption（把短标签扩写成密集描述）、编辑指令（描述两张图的差异）、组图描述（先述共性再逐张）；
  • 人工密集描述：质量最高的一批，留给训练收尾阶段。

评估方式照搬 CAPability 框架：在动作、镜头角度、镜头运动、物体类别、颜色、计数、OCR、场景、风格、事件十个维度上各抽 1000 条视频，与 Google Gemini 1.5 Pro 的 caption 逐维算 F1。结论是互有胜负——自家模型在事件、镜头角度、镜头运动、风格、颜色上更强，Gemini 在动作、OCR、场景、类别、计数上更强。注意 「镜头角度、镜头运动、风格」恰好是 Wan 赢的三维：caption 体系为视频生成量身定制的取向，在这里就埋下了。

其一，数据规模。相对 2.1，图像 +65.6%、视频 +83.2%——第 2 章的对比表已列过，这两个数字的直接回报是运动、语义、美学三个维度上的泛化提升。视频侧近九成的增幅配合表 9-2 的运动分桶，就是「复杂运动生成」卖点的来源。

其二，美学数据策略。博客原话：Wan 2.2 纳入了「精心筛选的美学数据，带有光线（lighting）、构图（composition）、对比度（contrast）、色调（color tone）等维度的详细标签」（meticulously curated aesthetic data, complete with detailed labels for lighting, composition, contrast, color tone, and more），由此实现「更精确、可控的电影风格生成，产出符合定制美学偏好的视频」。落到机制上：9.2 的 caption 模型本来就标镜头角度、风格、颜色，2.2 把标注维度扩展到这组电影语汇，让「怎么打光、怎么构图」在训练分布里成为可被文本指名的坐标。

为什么「打标签」能变成「可控性」

美学标签起作用的路径不在数据本身，而在图文对齐：caption 模型用「光线、构图、对比度、色调」这套语言描述了每条训练视频 → umT5 的嵌入空间里，这些维度是真实存在、高频出现的语义方向 → 推理时在 prompt 里写「侧逆光、三分法构图、低对比、暖色调」，cross-attention 能直接对上训练分布里的同类样本。美学控制不是外挂的风格 LoRA（第 8 章 Animate 的重打光 LoRA 是另一回事），而是长在语言对齐里的原住民能力。第 10 章的 prompt 指南会给出对应的写法建议。

其三，MoE 训练。2.2 官方对两专家怎么训的披露很少，主要证据仍是第 3 章 3.4 节引过的消融：Wan2.1 可以充当任意一个专家、且与新专家任意组合都优于基线——说明两个专家结构相同、接口兼容、可独立替换，各自是对同一基线在对应噪声区间上的继续优化，衔接处靠训练分布的连续性而非路由网络（第 3 章已详述）。美学标签与这种分工天然互补：布局与构图主要在高噪段定调，光线质感与色调细节主要在低噪段打磨——一个专家管「拍什么」，另一个管「怎么拍得好看」。

评测侧配套换了新基准 Wan-Bench 2.0：博客用它把 2.2 与多家闭源商业模型按关键维度公平对比，结论是全面领先。基准的具体维度构成未随博客公开，官方也只放出胜出的雷达图——2.2 真实的短板讨论，见第 11 章。

9.4 训练课程：低分辨率起步，分辨率阶梯爬升

报告 §4.2.2 给出的预训练配方不走捷径——先当图像模型，再当视频模型。理由非常工程化：直接上高分辨率长视频联合训练有两个坑，其一，序列太长（1280×720 的 81 帧视频）导致训练吞吐骤降，固定 GPU 小时预算下喂不够数据、收敛变慢；其二，显存被吃爆只好缩小 batch，梯度方差尖峰会让训练失稳。对策是课程学习：

VAE 也是同款课程（报告 §4.1.2，Wan2.2-VAE 亦沿用此法）：先训一个同结构的 2D 图像 VAE；把它膨胀成 3D 因果 VAE，在 128×128、5 帧的低规格视频上训练（从零训视频 VAE 慢得多，图像先验能大幅加速收敛）——损失为 L1 重建、KL、LPIPS 感知三项，权重 3 : 3e-6 : 3；最后在多分辨率、多帧数的优质视频上微调，并加入 3D 判别器的 GAN 损失抠细节。第 4 章读过的 encoder/decoder 结构，就是在这个课程终点被固定下来的。

9.5 基础设施：十万级 token 序列的训练账本

训练时只优化 DiT——T5 文本编码器与 VAE encoder 全程冻结，因此算力与显存都集中在 DiT 上（占训练总计算量 85% 以上）。报告 §4.3 先算了两笔账，这两笔账决定了后面全部并行设计：

计算账。DiT 单层计算量近似 L·(α·b·s·h² + β·b·s²·h)：线性项随序列长 s 线性增长，注意力项随 s² 增长（非因果注意力下 β 前向 4、反向 8）。视频序列动辄数十万 token，s² 项迅速接管——序列到 100 万 token 时，注意力可占端到端训练时间的 95%。显存账：激活显存 ≈ γ·L·b·s·h，LLM 的 γ 约 34，DiT 因为输入多了视频 token、prompt、timestep，γ 可超过 60。两项合计的结论：14B DiT 在 100 万 token、micro-batch 取 1 时，仅激活就超过 8 TB——单卡装不下，单机也装不下。

并行账。于是模块各拿各的策略：VAE 显存小走纯数据并行（DP）；T5 要占 20 GB 以上显存，必须做权重量化切分；重头戏是 DiT 的四层嵌套——FSDP（参数、梯度、优化器态全切片）管住 14B 的权重本体，2D 上下文并行（2D-CP）管住序列维：外层 Ring Attention、内层 Ulysses。选内 Ulysses 外 Ring 的组合，是为了同时躲开两个坑——Ulysses 单独用跨机通信慢，Ring 单独用要求分块后块还很大；内外分工后，256K token、2 机 16 卡的场景下，通信开销从 Ulysses 的 10% 以上压到1% 以下。第 7 章推理侧的 USP（Ulysses + Ring 序列并行）就是这套训练技术的同族后裔。

128 GPU 拆账：DP = 4（数据副本） × FSDP = 32（权重分片组） × CP = 16（序列切分 = Ulysses 8 × Ring 2） → 全局 batch = 8 × micro-batch；FSDP 组与 CP 组相交，DP = FSDP ÷ CP

还有一个容易被忽略的机关：不同模块间要切换分布式策略。VAE 与 T5 走 DP、DiT 走 DP+CP，而 CP 要求组内各卡吃同一批数据——若 VAE/T5 也按 CP 组读同一批，就重复计算了。做法是 CP 组内的卡先各读不同数据，进 CP 前按 CP 大小轮转广播对齐。这一手把 VAE 与 T5 在单次迭代中的时间占比压到 1/CP。

显存策略上一反常规直觉：不用梯度检查点优先，而用激活卸载（offload）优先。理由还是那笔计算账——长序列下计算时间远超 PCIe 传输时间，卸载一层 DiT 激活的传输可以和 1~3 层 DiT 的计算重叠，是「白捡」的显存；梯度检查点（重算换显存）只作为补充，优先用在显存/计算比高的层。最后托底的是阿里云集群的工程化：智能调度、慢机检测、故障节点隔离自愈、任务自动重启续训——训练基础设施不是把 GPU 摞起来，而是让几千张卡在数周尺度上不掉链子。

训练侧的拼图至此完整：四层漏斗选出数据（§3.1/3.2），caption 模型写就描述、标好镜头语言（§3.3），2.2 在其上扩出美学标签与近九成的视频增量；课程学习控制成本爬到 720p，FSDP 与 2D-CP 把十万级 token 的注意力搬进几百张卡的怀抱。下一章换到使用者视角：这些模型怎么在本地跑起来。

所有任务共用 generate.py：单卡模式挂三个省显存开关——--offload_model True（模块在 CPU/GPU 间按需轮换）、--convert_model_dtype（权重转成 config 的 param_dtype，即 bf16）、--t5_cpu（umT5 编码器放 CPU）；多卡模式改用 torchrun 加 --dit_fsdp --t5_fsdp --ulysses_size N（FSDP 权重切分 + Ulysses 序列并行，第 7 章已拆解），此时不再需要省显存开关。下面按任务给最小可用命令，均为 README 原样命令。

（1）T2V：文生视频基线

单卡（≥80GB）· 720P 文生视频Bash

10.3 Prompt 写法：把美学标签变成画面

第 9 章那个 callout 留了个尾巴：「推理时在 prompt 里写侧逆光、三分法构图、低对比、暖色调，cross-attention 能直接对上训练分布里的同类样本」——本节给出具体写法。心法只有一句：写 prompt 就是在模仿 Dense Video Caption 的输出分布。第 9 章列过 caption 模型的十维（动作、镜头角度、镜头运动、类别、颜色、计数、OCR、场景、风格、事件），prompt 覆盖的维度越多、措辞越像「模型见过的描述」，生成就越稳。

官方 I2V 示例那条白猫 prompt 正是这个路数，拆开看五层结构：

  • 主体与场景：a white cat wearing sunglasses sits on a surfboard——角色 + 道具 + 动作；
  • 表情与视线：gazes directly at the camera with a relaxed expression——「看镜头」直接对应镜头角度维度；
  • 背景与景深：Blurred beach scenery ... crystal-clear waters, distant green hills, and a blue sky——「虚化背景」是光圈语言，背景分了三层远近；
  • 姿态与情绪：naturally relaxed posture, as if savoring the sea breeze——动作之外的体态；
  • 镜头语言收尾：A close-up shot highlights ...——特写 + 强调细节，正是镜头运动维度。

五层依次递进，一句话一个维度。在此基础上，把 2.2 美学数据的四个标签维度写进去，就触发了第 9 章说的「长在语言对齐里的可控性」。博客只点名了维度名（lighting / composition / contrast / color tone）没公开词表，下表按摄影与电影工业的通用语汇整理常用写法：

11.2 从 2.1 到 2.2：使用者的实际收益

第 1 章总结过「三个不变、四个升级」，现在从使用者视角把账收拢成三条实打实的收益：

  • 同预算下更强的模型：MoE 把总参做到 27B，但每步激活成本仍是单个 14B——2.1 时代 80 GB 单卡跑 14B，2.2 同样的卡跑双专家（第 3 章），质量上限抬高了，门票价没涨；
  • 消费级显卡第一次拿到 720P@24fps：2.1 的消费级选项是 1.3B（能力有限），TI2V-5B 用 16× 压缩 VAE + 统一 T2V/I2V 设计（第 4、5 章）让 4090 档位拿到接近旗舰档的规格；
  • 美学可控变成可写的语言：2.1 的 prompt 主要控「拍什么」，2.2 增加了「怎么拍」的维度（光线、构图、对比度、色调），第 10 章 10.3 的词表就是这笔收益的用法；配套的数据增量（图像 +65.6%、视频 +83.2%）则让运动与语义泛化更稳。

至于与闭源模型的对比，博客用 Wan-Bench 2.0 给出了「全面领先开源与闭源」的结论。这里建议保持一份清醒：基准的具体维度构成没有随博客公开，官方自建自评的对比天然有立场。但开源模型有一张闭源模型永远拿不出的底牌——11.1 那张生态表：五任务四件套的完整度、九个社区项目的活跃度、双框架同日集成的工程节奏，这些第三方用脚投票的证据，比自建雷达图更硬。

11.3 局限：雷达图的背面

兑现第 9 章的伏笔。谈局限前先交代出处：2.2 没有发布新的技术报告，官方正式承认的局限清单仍写在 2.1 报告 §6 里（arXiv:2503.20314），以下逐条对照 2.2 的增量，看哪些被缓解、哪些仍是结构性的。

局限一：大运动下的细粒度保真。报告承认「大幅运动场景中保持细粒度细节仍是难点，也是全领域的共同问题」——文字会碎、人脸手部会糊。2.2 用 +83.2% 的视频数据把运动泛化推得更稳（博客把它列为主要增量之一），但这个问题是结构性矛盾：运动越大、每帧可积累的细节越少。有意思的是 Wan 自己的解法方向：绕开纯文本控制，改用显式条件兜住细节——S2V 用音频 + 参考图锁定身份口型（第 8 章 8.2），Animate 用姿态 + 人脸视频锁定动作与表情（8.3），社区侧的 Prompt Relay 则从时序上把运动拆成逐段可控。文本生视频的原生细节保真，仍留待下一代。

局限二：推理成本。报告原话：「14B 模型在单张高端 GPU 上不加优化约需 30 分钟」——这是 2.1 时代的数字，2.2 的回应是两条腿：MoE 让容量翻倍而激活成本不涨，TI2V-5B 把 720P@24fps 压进 24 GB 消费卡。而真正把成本打下来的是社区：LightX2V 的步数蒸馏、Cache-dit 的缓存加速（且已适配 2.2 MoE）、FastVideo 的稀疏注意力——开源生态自己消化了成本问题，这是 11.1 表格与这条局限的对应关系。

局限三：领域专业知识不足。报告承认作为通用基础模型，教育、医疗等垂直场景的表现可能不够，给出的药方是「开源最新模型、以社区驱动的方式覆盖多元专业领域」。2.2 半年间的生态恰好是照方抓药：DiffSynth-Studio 提供 LoRA 与全量训练支持，社区项目能拿 5B 模型做垂直研究（TalkVerse）——垂直能力的补全路径已经铺好，但补没补上、补到什么程度，取决于社区而非官方。

报告里还有一条容易被漏掉的诚实记录：音效侧刻意剔除了语音数据——2.1 的配音能力无法生成人声（说话、笑、哭），因为训练数据特意排除了语音。2.2 的 S2V 从「音频 → 说话口型视频」的方向补上了半边；但反过来「视频 → 语音音轨」（给生成视频配音说话声）在 Wan2.2 仓库中仍无对应任务，这是五任务版图外的一块显式留白。

把三条局限合起来看，会发现它们的官方解药是同一个词：开源。成本靠社区加速消化，垂直能力靠社区训练补全，细节保真靠显式条件与控制类研究绕行。Wan 2.2 半年间从三模型长成五任务全谱系、Todo List 全勾的生态，与其说是模型的成功，不如说是「把模型开放出来」这个决策的复利。至于这套复利能滚多久、下一代的文本生视频能不能原生的解决细节保真——那是 Wan 2.3（或者别的名字）要回答的问题。本文档的正文到此收笔，最后一章留给参考资料与阅读路线。

12.3 结语

回头看，Wan 2.2 与 2.1 一样，没有发明任何一个全新的架构——3D 因果 VAE、DiT、Flow Matching、adaLN、RoPE、CFG、MoE 全都是已有组件。它做的事仍然是：在视频这个具体战场上，把每个组件都选到当前最优解，再用十亿级数据的笨功夫把上限顶上去。2.2 特有的两笔，一笔管效率——MoE 让容量翻倍而单步成本不涨；一笔管表达——美学标签把「怎么拍」的控制权写进了语言。读它源码的额外收获也在这里：你会看到「工业级 AI 系统」的真实形态——核心数学出奇地简单（第 2 章十分钟就讲完了），工程细节密密麻麻，而两者之间的每一处衔接（一次 timestep 拆分、一段 mask 覆盖、一个专家切换点）都是团队真实调过、想清楚过的证据。

希望这份文档帮你建立起从公式到代码的完整心理地图。接下来最好的学习方式只有一个：在一张 24 GB 的卡上跑通第 10 章那条 ti2v-5B 命令，然后打开 wan/textimage2video.py，在第 5 章那个 50 步的去噪循环里打断点，亲眼看首帧的 mask 如何在每一步把 latent 覆盖回去。视频生成的黑箱，从此对你透明。
