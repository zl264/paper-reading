MotionCtrl：用 RT 与稀疏轨迹分别控制相机和物体运动

从 world-to-camera 外参、Temporal Transformer 融合到 VideoCrafter 主分支的可复现输入接口

版本与证据范围：本文依据 MotionCtrl 论文 arXiv:2312.03641v2（2024-07-16）、SIGGRAPH 2024 论文附录，以及官方 TencentARC/MotionCtrl 的 main（VideoCrafter/LVDM）快照 6242d55414d3f4ad690bf0934889660f78e81b6e（2025-02-19）。svd、animatediff 分支及 VideoCrafter2 后端不混作本页 main 实现。本页核对论文与源码，不声称在本地执行模型训练、推理或性能测量。

任务定义与输入：一条 RT 序列，而不是相机运动标签

MotionCtrl 以文本提示 c 为内容条件，把通常混在一起的“镜头运动”和“被摄物体运动”拆成两条条件通路。前者由相机位姿序列指定，后者由物体在画面中的轨迹指定；两者可以单独开启，也可以同时开启。它不是一个把视频重投影到新视角的显式三维渲染器：输入没有参考 RGB、深度图、点云或 mesh，视频内容仍由文本驱动的潜空间视频扩散模型生成。

这个区分决定了它能回答的问题：例如“同一只马沿给定屏幕轨迹运动，同时相机向右移动”，CMCM 负责全场景随时间的视角变化，OMCM 负责局部对象在画面中的路径。论文的泛化主张是同一套训练权重接收不同位姿和轨迹，而不是为每一种预定义运动单独微调；它并不意味着任意物理上冲突的两个条件都能被精确实现。

逐帧 W2C 外参的严格展平顺序

设第 i 帧的 world-to-camera（W2C）变换为 Twc,i = [Ri | ti]，其中 Ri ∈ R3×3、ti ∈ R3×1。对列向量三维点有 pc,i = Ripw + ti。t 是世界原点在相机坐标系中的坐标，一般不等于相机中心；后者为 Ci = −RiTti。把 camera-to-world 矩阵直接传入会同时弄错旋转方向和这两个平移量的关系。

RTi = [r00 r01 r02 tx ; r10 r11 r12 ty ; r20 r21 r22 tz]；vec(RTi) = (r00, r01, r02, tx, r10, r11, r12, ty, r20, r21, r22, tz)(1)

即逐行展平 3×4 矩阵，在每一行末尾插入该行平移，不是先列九个 R 再列三个 t，也不是 OpenCV 序列化中有时使用的 rvec || tvec。默认视频长度 F=L=16，JSON 是嵌套的 [16][12] 数值列表，读成 [F,12]；motionctrl_inference.py:82–100 没有重排或内参处理，motionctrl_inference.py:145–154 再扩展为 [B,F,12,1]。这个最后的 1 被 CMCM 展平掉，不代表有一维空间坐标。

没有 K，也没有隐式可填写的 K 槽位。main 的模型条件只有 12 个外参数，不接收焦距 fx, fy、主点 cx, cy 或 K ∈ R3×3。因此它不能从同一 RT 推导不同视场角的精确透视效果，不能把“分辨率改变但 K 相应缩放”当作网络可见的条件变化。这里的控制是训练数据分布上的生成式条件，不保证针孔相机渲染等式在输出像素上严格成立。

坐标系、参考系、平移尺度与时间

约定main 中可以确定的事实自定义输入时必须避免的错误
变换方向app.py 的注释和随附轨迹将平移方向标为 W2C；网络接收 [R|t]。方向表不要把 C2W 直接当 RT；若源数据是 C2W，应对完整齐次矩阵求逆后取上三行。

帧间与首帧相对随附 test_camera_R.json 第一帧是单位旋转但非零平移；生成器也按 i/n 累进。示例首帧不要默认强制第一帧为零。create_relative 只用于相机可视化，不在送入模型前调用。
离散时间默认 16 个 RT 与 16 个 latent 时间位置按索引对齐；输出以 fps=10 写 MP4。保存代码不要声称 16 帧对应 1.6 秒的实时采集轨迹；fps 是输出封装设置，main 没有 RT 时间戳输入。
轴约定camera_utils.py 使用标准右手旋转矩阵 RzRyRx；但 main 未对 COLMAP/OpenCV/OpenGL 外部源做自动转换。坐标轴翻转到右手 W2C 后仍需核查正方向；不存在一个通用“加负号”按钮适合所有源数据。

以上未由 main 明确规定的部分不能靠猜：论文把 RT 定义为 L×12，但没有给出外部任意相机日志的统一轴变换或米制换算规则。工程上应先固定一个坐标约定，生成静态 RT 与随附简单轨迹做对照，再验证 R 的正交性、行列式和时序连续性。

整体结构与 CMCM：位姿进入第二个时序自注意力之前

图 1：依据 main 源码重绘的数据流，不是论文原图。BHW 是 batch 与 latent 空间位置的合并维，C 随 U-Net 层改变；OMCM 的输入大小采用默认 256² GUI 路径。

基底的 2D autoencoder 将每帧编码到 latent，默认初始噪声为 [B,4,16,32,32]；U-Net 的空间卷积/空间 Transformer 建模画面内容，Temporal Transformer 把每个空间位置单独变成 16 个时间 token。MotionCtrl 在运行时替换 U-Net 和 Temporal Transformer 的 forward，通过 context 字典将 pose_emb 透传到时序块，而没有改写整个扩散框架。

拼接、投影、自注意力的精确形状

论文把同一操作写成 RT ∈ RL×12 → RH×W×L×12，与 yt ∈ RH×W×L×C 沿末维拼接。main 中对应的内存排列更明确：[B,C,F,H,W] → [BHW,F,C]，位姿 [B,F,12,1] → [B,F,12] → [BHW,F,12]。注意 repeat 在 batch 维上做 repeat_interleave(HW)，所以每条样本的每帧位姿复制到所有空间位置；同一个位姿绝不会沿 token 维被误当成 16 个不同通道。

ỹb,s,i = Wfuse[ yb,s,i ; vec(RTb,i) ] + bfuse；Wfuse ∈ RC×(C+12)；i=0,…,F−1，s=0,…,HW−1(2)

OMCM 边界：二维轨迹特征加到编码器，不承担显式相机几何

论文中一条物体轨迹是每帧一个 (xi,yi) 的屏幕位置序列。为了把路径和速度都暴露给网络，i>0 帧在上一帧位置 (xi−1,yi−1) 写入位移 (u,v)=(xi−xi−1,yi−yi−1)；第 0 帧和轨迹没有经过的位置为零。多条轨迹可写入同一个两通道图。论文定义 Trajs ∈ RL×Ĥ×Ŵ×2，其中 Ĥ、Ŵ 是 zT 的网格尺寸；这与 main 的 GUI 预处理不能直接画等号。

论文与 main 的分辨率差异：main 的 traj_utils.py:82–104 先构造 [16,256,256,2] 位移图，在帧 i+1、上一位置 (y,x) 填位移，并以 99×99、σ=10 的归一化 Gaussian kernel 卷积帧 1…15。随后 app.py 转为 [B,2,16,256,256]。Adapter 的第一层 PixelUnshuffle(8) 才把空间边长降到 32，同时把 2 通道扩为 128。若自制 .npy，必须明确自己采用的是哪条接口，不能把论文 latent-grid 尺寸原样塞给 main 的 GUI。

def get_flow(points, video_len=16):
    optical_flow = np.zeros((video_len, 256, 256, 2), dtype=np.float32)
    for i in range(video_len-1):
        p = points[i]
        p1 = points[i+1]
        optical_flow[i+1, p[1], p[0], 0] = p1[0] - p[0]
        optical_flow[i+1, p[1], p[0], 1] = p1[1] - p[1]
    for i in range(1, video_len):
        optical_flow[i] = cv2.filter2D(optical_flow[i], -1, blur_kernel)
    return optical_flow

blur_kernel 在 traj_utils.py:37–43 定义；其归一化见 flow_utils.py:47–69。GUI 内部以 0…1023 的画布坐标收集点，插值到 16 个采样位置后除 4 取整到 256²。落点重复、反向或相互交叉的多轨迹会共享同一栅格；官方函数 process_traj 实际只接收一组点，不应把“模型支持多条轨迹”误写成这个 UI 支持分别指定多个对象身份。

lvdm_modified_modules.py:93–112 把这些特征在 input block 编号 2、5、8、11（即第 3、6、9、12 个 block）之后直接相加。默认 sk=true 的 Adapter 使用卷积与残差组合，但这里没有每尺度独立的 zero-conv 门控，也没有注入 U-Net decoder 或 middle；skip connection 后续可以把 encoder 中的轨迹信息送到 decoder，却不是 OMCM 在 decoder 再插一次。

所谓“解耦”因此是条件表示、注入位置和分阶段优化上的结构解耦，不是输出像素的数学独立性。RT 可以经 Temporal Transformer 影响整段视频的内容组织，物体轨迹也可通过 U-Net 的全局注意力影响背景；网络没有 3D scene state，也没有把前景图层和背景图层分别渲染。联合条件时两种语义仍可能互相牵制。

训练：先用 RealEstate10K 学相机，再冻结它学习物体

MotionCtrl 不依赖同时具有文本、准确相机外参、物体轨迹三者的数据集，而是构造两套弱增强数据并顺序训练。基本去噪目标仍是 epsilon 预测，而非显式重投影或位姿回归：

zτ = √(ᾱτ)z0 + √(1−ᾱτ)ε；L = Ez₀,c,m,ε,τ[ ||ε − εθ(zτ,τ,c,m)||²2 ]，m={RT,Trajs}(3)

这里用 τ 表示扩散步，以区别外参平移 t；ᾱτ=∏j=1…ταj。m 按训练阶段只包含一种或两种运动条件。main 的 ddpm3d.py:687–742 保留 parameterization="eps" 时的噪声 MSE 路径，配置中另列 uncond_prob=0.1 和 uncond_type=empty_seq；但 main 没有将论文两阶段运动数据完整接入 training loop 的脚本，不能把这份 YAML 视作一键复现训练的完整证据。

阶段数据构造可训练 / 冻结论文报告的配置
CMCMRealEstate10K 原本有 60K 以上视频和较干净位姿；对首帧、1/4、1/2、3/4、末帧用 Blip2 生成 caption 并拼接成片段描述。训练新增 MLP/cc_projection 和 Temporal Transformer 的第二个 self-attention；冻结 LVDM 其他部分。通常约 50K 次迭代收敛。
OMCM dense 预热从 WebVid 每个视频随机取 32 帧，跳帧间隔 s∈[1,16]；ParticleSfM 的动态轨迹分割生成约 243K 个片段的轨迹，保留原 caption。冻结已训练的 LVDM 与 CMCM，只训练 OMCM。20K 次迭代。
OMCM sparse 微调每段从稠密动态轨迹随机选 n∈[1,N] 条，N=8；对过于分散的稀疏轨迹使用 Gaussian filter。同上，不重新联合微调全部网络。再 20K 次迭代。

两阶段共同设置是 Adam、全局 batch size 128、学习率 10−4、8 张 NVIDIA Tesla V100，论文训练片段为 16 帧、256×256。这些是论文报告而非本页实测。RealEstate10K 的“自动生成文本”不是人类逐帧标注；WebVid 的“物体轨迹”来自 ParticleSfM 的运动分割，不是完整 3D 物体跟踪真值，误差会进入控制器训练。

顺序有实际优化含义：如果先训 OMCM，再训 CMCM，后者会改动 Temporal Transformer 的第二个 self-attention，破坏 OMCM 已适配的参数环境；反过来则 OMCM 阶段将 CMCM 固定，避开这个问题。消融中 dense-only 的 ObjMC 为 54.4114，sparse-only 为 34.6937，dense→sparse 为 25.1198（均为论文数值，越低越好）；这里支持的是训练分布匹配，不等于所有稀疏路径都能稳定控制。

公开数据准备脚本只封装 ParticleSfM 的光流、点轨迹连接和动态运动分割，并把官方 SfM 重建调用注释掉，见 run_particlesfm_obj_traj.py:136–161。附录报告 ParticleSfM 处理一个 32 帧视频约需 2 分钟，因而采用稀疏时间采样。这是离线标注开销，不是 MotionCtrl 的 16 帧推理耗时。

推理与自定义轨迹：直接构造 tensor，绕过 GUI 的隐式缩放

一次推理先编码文本，把 RT 变成 [B,16,12,1]，再把 OMCM 特征在采样之前计算一次。之后 DDIM 的每一步都把这些条件送入同一个 U-Net；条件本身不随扩散时间步变化。采样结果 [B,4,16,32,32] 逐帧经 2D autoencoder 解码为 [B,3,16,256,256]，不是先生成一张首图再 warp。

Gradio RAW 不是原样矩阵输入：camera_utils.py:98–110 会检查 16×12 个浮点数、reshape 为 [16,3,4]，再将平移乘以 [1.5,1,1.3] * speed。虽然 app.py:413–416 帮助文字误写“14 lines”，实际断言要求 16 帧。要原样输入，应走 JSON loader 或直接调用 motionctrl_sample 的 tensor 接口。

讲解用实现 / 伪代码 · 非官方源码：原样 RT 与自定义屏幕轨迹
import json
import numpy as np
import torch

F = 16

def load_w2c_tensor(json_path, batch_size=1):
    with open(json_path, "r", encoding="utf-8") as f:
        values = np.asarray(json.load(f), dtype=np.float32)
    assert values.shape == (F, 12), values.shape

    rt = values.reshape(F, 3, 4)       # 每行 [r0,r1,r2,t]
    rotation = rt[:, :, :3]
    assert np.allclose(rotation @ rotation.transpose(0, 2, 1),
                       np.eye(3, dtype=np.float32), atol=1e-4)
    assert np.allclose(np.linalg.det(rotation), 1.0, atol=1e-4)
    assert np.allclose(rotation[0], np.eye(3), atol=1e-5), "先核查参考系"
    poses = torch.from_numpy(values).unsqueeze(0)  # [1,16,12]
    return poses.repeat(batch_size, 1, 1)

def one_pixel_trajectory(points_256, height=256, width=256):
    """points_256[i]=(x,y)；不做 GUI 的 1024→256 或 RAW 平移缩放。"""
    assert len(points_256) == F
    points = np.asarray(points_256, dtype=np.int32)
    assert np.all(points >= 0) and np.all(points < [width, height])
    flow = np.zeros((F, height, width, 2), dtype=np.float32)
    for i in range(1, F):
        x0, y0 = points[i - 1]
        x1, y1 = points[i]
        flow[i, y0, x0] = (x1 - x0, y1 - y0)
    # 实际 main GUI 还在此处用 99×99、sigma=10 的 Gaussian 卷积。
    return torch.from_numpy(flow).permute(3, 0, 1, 2).unsqueeze(0)

camera_poses = load_w2c_tensor("examples/camera_poses/test_camera_R.json")
points = [(48 + 8 * i, 128) for i in range(F)]
trajs = one_pixel_trajectory(points)                # [1,2,16,256,256]
noise_shape = [1, 4, 16, 32, 32]

这个例子故意保留稀疏单点位移，方便核对索引，并不等价于已微调的官方 GUI 输入分布；实际复现宜先调用官方 process_traj 生成 Gaussian 位移图。若直接 motionctrl_sample，JSON 不再经过 RAW 的平移乘数，[B,16,12] 是正确输入。用多个对象时，需要在同一 flow 图中加入多条轨迹；要处理遮挡或交叉，必须另外设计冲突规则，官方单线 GUI 并未解决这一层问题。

能力边界、计算代价与代表方法比较

哪些“3D 一致性”能由 RT 提供，哪些不能

位姿序列提供跨帧的全局几何归纳偏置：所有 latent 空间位置共享同一帧 RT，时序注意力可以学习一致的视差、推进和旋转模式。但网络看不到 K、深度或场景三维状态，输出也没有经过多视图重投影约束。因此遮挡处的新内容、远近物体不同视差、焦距改变或严格度量尺度仍由生成先验补全。这里的“3D 一致性”应理解为从 RealEstate10K 位姿—视频对中学习的统计一致性，而不是经过结构光束法平差或渲染一致性损失的证明。

  • 联合控制的失败模式：论文明确报告，同时要求复杂相机与复杂物体轨迹时需要精心设计二者，自然协调结果的成功率相对较低。这不只涉及跟踪误差：在相机大位移时仍要求屏幕空间物体走固定路径，可能隐含互相竞争的场景运动。
  • 尺度与外推：缺少米制或深度条件意味着同一平移值可能对应不同语义幅度；远离训练位姿的旋转、长轨迹和大尺度平移不应预期仍精确。16 帧硬编码也限制直接长视频控制。
  • 轨迹不携带身份：OMCM 的二维流没有对象 ID、3D 深度或遮挡状态，文本负责对象语义；相同流可被不同 prompt 解释为不同物体，但不能保证指定多对象后的对应关系。
  • 数据噪声和外观：RT 本身 appearance-free，但 RealEstate10K 场景单一，文本依赖 Blip2；ParticleSfM 分割不完美，冻结策略只是减少而非消除对基底生成质量的影响。
  • 推理开销：CMCM 每个时序块增加 C+12→C 的逐 token 投影，并让 RT 影响两次 CFG 前向；OMCM 先对每帧高分辨率位移图做一次多尺度编码，再共享给各 DDIM 步。相对只跑原 U-Net，这些不是零成本；main 没有可靠的统一显存/延迟基准，本页不给出虚构数字。
方法运动条件与几何与 MotionCtrl main 的真实差别
AnimateDiff Motion LoRA从模板视频学习八种基本镜头运动，各用独立 LoRA。MotionCtrl 直接给 16 个连续 RT，可用幅度改变速度并组合复杂路径；论文也展示过 AnimateDiff 移植，但那不是 main 的同一个实现。
VideoComposer从参考视频得到 motion vectors，以统一条件描述运动。向量可能同时编码相机、物体和轮廓；MotionCtrl 用外参与稀疏轨迹分路，减少把参考门的外形错误转移到生成对象的情况。
DragNUWA文本、首图和轨迹控制视频。轨迹来自光流，论文指出其不明确区分前景物体与背景运动；MotionCtrl 在架构及训练阶段显式分离二者。
CameraCtrl逐像素 Plücker 射线编码，通常同时依赖 R、t 与 K。MotionCtrl 是每帧仅 12 维外参，复制到 latent 位置后做时序融合；不能用 CameraCtrl 的六通道射线张量替换 RT，也不能将“无 K”说成两种方法共有性质。
GEN3C 类三维生成方法利用深度、点云/缓存和显式 warp 为新视角提供场景内容。MotionCtrl 不维护几何缓存，结构更轻，但不提供同等意义上的显式可见性、遮挡和度量几何约束。

论文实验中 MotionCtrl 的基本/复杂位姿 CamMC 分别为 0.0289/0.0735，优于其 AnimateDiff 与 VideoComposer 对照；对象 ObjMC 为 28.877。所有数值由生成视频再经 ParticleSfM 估计位姿或轨迹后计算欧氏距离，因此评价估计器也会影响结果，不是逐像素满足输入矩阵的误差。注入位置消融支持时序模块：Temporal Transformer 的 CamMC 0.0289，而 time embedding、spatial cross-attention、spatial self-attention 分别为 0.0887、0.0857、0.0902。它们是论文在指定数据集、基底和设置下的对照，不能外推成对所有新模型的普遍排名。
