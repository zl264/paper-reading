论文的核心反驳

“Plücker 比 RT 好”不是充分解释。相同的高维相机融合下，RT 也能有效控制；相反，把低维位姿简单拼到 DiT token 中，可能因条件通道占比太低而被视频特征淹没。真正需要同时优化的是表示、投影、注入与推理 guidance。

1. 为什么把 MotionCtrl / CameraCtrl 直接搬到 DiT 会退化

OpenSora 的 ST-DiT 将空间和时间注意力组织为 Transformer block。DiT-MotionCtrl baseline 把每帧 RT 重复到空间 token 后拼接；DiT-CameraCtrl baseline 则使用相机 encoder 将 Plücker 投到高维并与特征相加。

作者把 condition-to-channel ratio 作为关键观察：若视频 token 有数千维而相机只占 12 维，拼接后的可学习投影未必会分配足够权重给这 12 维。高维、空间变化的相机表示提供更多可学习参数和空间对齐信息，控制更容易被网络使用。

方案条件形态融合论文诊断
DiT-MotionCtrl每帧 12 维 RT空间复制后与 token 通道拼接低维条件容易淹没
DiT-CameraCtrlPlücker 图encoder 后与特征相加、再投影高维空间条件更有效
相同融合 + RTRT 经高维映射保持高维融合说明 Plücker 并非唯一关键

2. RT 与 Plücker 各自表达什么

RT 直接表示坐标变换；Plücker 表示每个像素的三维射线。两者经合适网络都能提供几何信息，差别在于先验落在“输入表示”还是“网络学习”上。

RTf = flatten([Rf|Tf]) ∈ R12(1)
Plückeru,v = [O×du,v, du,v] ∈ R6，  O=−RTT(2)

这里 O 是世界系相机中心。一个实用的实验不是只比较两种输入，而是固定主干、参数量、注入位置和训练数据，再分别替换表示，才能定位差异。

3. Camera Motion Guidance：把相机从文本 CFG 中分离

普通 CFG 通常只比较正文本和负文本，两个分支都有相机。这只能加强语义方向，不一定增加轨迹遵循。CMG 使用三个预测：

  • e₀₀：空文本、空相机；
  • e₁₀：正文本、空相机；
  • e₁₁：正文本、目标相机。
ê = e₀₀ + sT(e₁₀−e₀₀) + sC(e₁₁−e₁₀)(3)

第一项提供基础分布，第二项沿文本方向移动，第三项沿相机方向移动。主实验相机 guidance 取 5；该数值是论文实验设置，不是所有模型的最优常数。与两次前向的普通 CFG 相比，三分支增加推理成本。

讲解用实现 · 非官方源码：CMG 采样步
def cmg_step(dit, latent, t, text, null_text, camera, null_camera,
             text_scale, camera_scale):
    e00 = dit(latent, t, null_text, null_camera)
    e10 = dit(latent, t, text,      null_camera)
    e11 = dit(latent, t, text,      camera)
    guided = e00 + text_scale * (e10 - e00)                 + camera_scale * (e11 - e10)
    return scheduler.step(guided, t, latent)
# camera_scale=0 时仍有 e11 前向；工程上可省略该分支。
# null_camera 的语义必须与训练 camera dropout 完全一致。

4. 训练与稀疏关键帧控制

基线沿用视频扩散损失，在 RealEstate10K 上以 16 帧、256² 训练 8 epochs；只更新时序 Transformer 和新增相机模块。训练新增两类相机制空：

  • null camera（5%）：重复首帧和首位姿，提供相机 CFG 的空条件。
  • camera dropout（5%）：随机将 70–100% 帧位姿置零，允许只给少数关键帧位姿。

后者不是普通的数据增强噪声，而是改变条件分布：模型学会在缺省相机帧上根据上下文插值运动。稀疏位姿的实际插值仍由生成模型完成，不是几何上的严格 SE(3) 插值。

讲解用实现 · 非官方源码：关键帧 mask 与条件构造
def sparse_camera_condition(poses, observed, fill=0.0):
    # poses: [B,F,12]；observed: [B,F] bool，标出真正指定的关键帧。
    condition = poses.clone()
    condition[~observed] = fill
    # 若需要模型区分“真实零位姿”和“未指定”，建议额外附加 observed mask；
    # 这是工程改进建议，不是论文已展示的额外界面。
    return condition, observed.to(poses.dtype)

# 推理时将同一 condition 传入 e11；e00/e10 使用训练约定的 null camera。

5. 局限与公平比较

这篇工作主要解决控制强度与 DiT 适配，不直接提供 3D cache、极线约束或显式遮挡处理。相机 guidance 增强可能带来画面质量下降、动态减弱或过强的几何运动，需要同时调节文本和相机尺度。

RealEstate10K 的静态与轨迹分布限制仍在；不能把该基准上的控制提升直接外推到开放域动态视频。论文项目页中的“code will be available”是发布意向，不能据此声称本文已核验官方训练代码。

6. 推荐消融实验

  1. 固定 Plücker，比较通道拼接、特征相加与独立 cross-attention。
  2. 固定高维融合，比较 RT 与 Plücker，避免把参数量差异算到表示头上。
  3. 分别扫描 sT、sC，记录轨迹误差和视觉质量，不只报告最优单点。
  4. 比较 0%、5%、更多 camera dropout，观察无条件分支是否落在训练分布内。
  5. 测量三分支前向的实际推理开销，再考虑引导缓存或蒸馏。

7. 一句话理解与使用建议

把 CMG 看成一种几何方向的 classifier-free guidance：文本决定生成什么，相机决定从哪里看。对已有 DiT 进行改造时，先确认条件被网络真正利用，再考虑换更复杂的位姿表示。

附录 A：三种“空相机”语义不能混淆

论文的首帧相对预处理把 R₁=I、T₁=0，后续 RT 乘上首帧逆矩阵。训练时 null camera 是重复首帧及首位姿，对应“没有额外相机运动”；zero camera 则把随机 70–100% 的帧置零，支持稀疏控制。二者虽然都是张量条件，却承担不同职责。

对于稀疏控制，用户可以提供第一、中间和最后帧的位姿，其余置零；模型从训练分布学习补全中间轨迹。93% 稀疏时误差明显增加，说明“支持稀疏”不是任意稀疏都不损失精度。

论文评价使用 COLMAP 重新估计生成视频的 R 和 T。旋转误差从第二帧开始计算；平移向量按最大距离归一化，因此指标主要比较运动方向与相对尺度，不等于绝对米制误差。Motion 用相邻帧光流幅值均值度量，会受画质、物体运动与纹理影响，不能独立代表相机控制精度。

代码 1：HighDimCameraCondition

HighDimCameraCondition · 保留条件通道比（讲解用实现，非官方源码）
class HighDimCameraCondition(nn.Module):
    def __init__(self, video_dim, camera_dim=6, condition_dim=None):
        super().__init__()
        condition_dim = condition_dim or video_dim
        self.encoder = nn.Sequential(
            nn.Conv3d(camera_dim, condition_dim//4, 3, padding=1),
            nn.GELU(),
            nn.Conv3d(condition_dim//4, condition_dim, 3, padding=1))
        self.merge = nn.Linear(video_dim + condition_dim, video_dim)

    def forward(self, video_tokens, camera, spatial_shape):
        # video_tokens: [B,F,HW,C]；camera: [B,6,F,H,W]
        B,F,HW,C = video_tokens.shape
        cam = self.encoder(camera)               # [B,D,F,H,W]
        cam = cam.flatten(3).permute(0,2,3,1)    # [B,F,HW,D]
        # 条件通道 D 与视频 C 同量级，避免 12 维被数千维淹没。
        return self.merge(torch.cat([video_tokens,cam],dim=-1))
# 若用 RT 代替 Plücker，先经过独立 MLP 扩展到相同 D，再比较才公平。

# 首帧相对化
relative_rt = np.linalg.inv(rt_absolute[0]) @ rt_absolute

for t in scheduler.timesteps:

附录 D：训练算法与梯度路径

采用 RealEstate10K、16 帧、256²、8 epochs；文本使用已有 CameraCtrl 标注。每个 GPU batch=3、lr=1e-5。模型只更新 temporal transformer 与新增相机模块。训练还使用中心裁剪和时间反转平衡相反运动方向。null camera 与 zero camera 是两种不同条件，不能都简单解释成“删除相机”。

读代码时的关注点：代码 1 用 3D 卷积把射线条件提升到与视频相近的维度，避免 12 维在数千维 token 中失去作用；代码 2 把首帧相对、null/zero camera 和 CMG 采样串起来。真实 OpenSora 还需 ST-DiT 的空间/时间打包与 scheduler，不应将这些教学类当成已发布实现。

附录 E：显式位姿推理流程

先准备正文本、空文本、目标相机与 null camera，再在每个采样步计算 e00、e10、e11。文本尺度固定 4，论文比较时相机尺度选 5；更高相机尺度通常增强运动，却可能降低画质。稀疏控制中把未指定帧置零，模型补全其余轨迹，93% 稀疏时误差已明显增加。

推理前要明确：位姿是 c2w 还是 w2c、是否首帧相对、K 是否像素单位、帧率是否经过 VAE 压缩，以及 unconditional 分支采用哪一种空相机。只把这些数值变成合法 shape 不足以保证几何正确。
